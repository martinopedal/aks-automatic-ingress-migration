02
Ingress is one box.
Gateway API is three.

Role separation. Cross-namespace by default. The mental model shifts before any YAML does.

Ingress resources are monolithic. Gateway API splits the concern into three resources with role separation: GatewayClass for the infra owner, Gateway for the cluster operator, HTTPRoute for the app developer. Better RBAC, clearer ownership boundaries.

Ingress, one resource, every concern.


apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: example
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx
  rules:
  - host: example.com
    http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service:
            name: api-service
            port:
              number: 8080

Annotations encode infra. Vendor coupling. No role separation.

Ingress mixes infrastructure decisions (TLS, load balancer flavor) with application routing (host, path, backend). Annotations are vendor-specific and not portable. ingressClassName arrived in Kubernetes 1.18 to allow multiple controllers per cluster, but it does not solve role separation.

Gateway API, three resources, three owners.


apiVersion: gateway.networking.k8s.io/v1
kind: GatewayClass
metadata: { name: azure-alb }
spec:
  controllerName: azure.com/alb-controller
---
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata: { name: example-gateway, namespace: infra }
spec:
  gatewayClassName: azure-alb
  listeners:
  - { name: http, protocol: HTTP, port: 80 }
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: { name: api-route, namespace: app }
spec:
  parentRefs:
  - { name: example-gateway, namespace: infra }
  hostnames: [example.com]
  rules:
  - matches:
    - path: { type: PathPrefix, value: /api }
    backendRefs:
    - { name: api-service, port: 8080 }
GatewayClass is the infra owner's resource (AGC controller). Gateway is the cluster operator's resource (SRE team) and defines listeners and TLS. HTTPRoute is the app team's resource and defines routing. HTTPRoute can reference a Gateway in another namespace. Cross-namespace routing as a first-class feature.

Annotation translation has a ceiling.

Patterningress2gatewayAGC native
Path rewrite✓ translates✓
CORS basic✓ translates✓
Rate limit, basic✓ translates✓
Custom auth annotations✗ no map✗ use Workload Identity
Lua / configuration-snippet✗ no map✗ not supported
Canary by header / weight✗ partialuse Argo Rollouts

kubernetes-sigs/ingress2gateway v1.0

ingress-nginx ships with over 100 annotations. Gateway API prefers first-class fields. ingress2gateway translates rewrite-target, CORS, basic rate limiting, and a few others. Many annotations (auth, custom headers, Lua snippets) have no equivalent. Audit your manifests, then decide per annotation: drop it, move to app, or block on a workaround.

Four things that don't translate.

✗ Lua configuration-snippet annotations. AGC has no Lua. Move logic into the app or a sidecar.
✗ Custom auth nginx auth-url, auth-snippet. Replace with Workload Identity and app-layer token validation.
✗ Advanced rate limit Per-IP, per-path, leaky bucket. AGC supports basic rate limiting only.
✗ Canary nginx.ingress.kubernetes.io/canary. Use Argo Rollouts or Flagger with Gateway API support.
If you rely on Lua for header manipulation or custom logic, move that into the app or use a sidecar proxy. For authentication, prefer Workload Identity with app-layer token validation. For canary, use progressive delivery tools that already integrate with Gateway API: Argo Rollouts, Flagger.

TLS, two ways.

Ingress
  • tls block on the Ingress resource
  • secretName references a kube Secret
  • Same namespace as the Ingress
Gateway API
  • TLS on the Gateway listener
  • Mode Terminate or Passthrough
  • Secret in the Gateway namespace
  • AGC pulls certs via Key Vault CSI

MS Docs: AGC SSL offloading

In Ingress, you define a tls block with a secretName pointing to a Kubernetes Secret. In Gateway API, TLS configuration lives on the Gateway listener with mode Terminate or Passthrough. The Secret must be in the same namespace as the Gateway. AGC integrates with Azure Key Vault, so the Key Vault CSI driver can sync certificates into Secrets automatically.

Readiness checklist before you cut.

  1. 01. Export every Ingress: kubectl get ingress -A -o yaml
  2. 02. Run ingress2gateway and read the generated HTTPRoutes
  3. 03. List every annotation that did not translate
  4. 04. For each annotation, decide drop, move to app, or block
  5. 05. Apply HTTPRoutes to a non-prod cluster first
Do not start the migration without a complete inventory. Use kubectl get ingress -A -o yaml to export everything. Run ingress2gateway and review the diff. For each annotation that did not translate, document the decision in an ADR or runbook addendum.
03
ALZ Corp is the constraint.

Private API, no public IPs, central firewall egress. AGC has to fit, not the other way around.

Azure Landing Zone Corp is the enterprise topology used by most large orgs. Hub VNet with Azure Firewall, spoke VNets for workloads, no public IPs on compute, private endpoints for PaaS. AGC must fit into this without breaking the security model.

The topology you're walking into.

  • Hub owns Azure Firewall, VPN, Bastion
  • Spoke hosts AKS plus a delegated AGC subnet
  • No public IPs on AKS nodes
  • Private cluster API server
  • Egress flows out via Azure Firewall UDR

Azure Landing Zones

Hub VNet is owned by central networking. Spoke VNet is owned by the workload team. AKS clusters run in spoke VNets with no public IPs. The API server is private (VPN or ExpressRoute). All egress from AKS pods is routed to Azure Firewall via UDR. AGC has to work inside that.

AGC needs a delegated subnet.

  • Subnet delegation: Microsoft.ServiceNetworking/trafficControllers
  • Recommend /24 or larger to fit control and data plane scale-out
  • Frontend mode: internal for ALZ Corp, private IP only
  • Front Door or AppGw in the hub fronts the AGC internal IP

MS Docs: AGC subnet requirements

AGC needs a subnet delegated to Microsoft.ServiceNetworking/trafficControllers. Size it /24 or larger for headroom. For ALZ Corp, configure AGC with an internal frontend (private IP). Place a public Front Door or Application Gateway in the hub and point it at the AGC internal IP. AKS nodes and AGC instances stay fully private.

Traffic path, edge to pod.

Traffic enters via Front Door in the hub. Front Door terminates TLS and runs WAF. It forwards to AGC in the spoke VNet. AGC terminates TLS again if configured and routes to the right pod. Egress from AKS pods goes through Azure Firewall via UDR. No public IPs on AKS, central egress control, defence in depth.

Workload Identity, no SP secrets.

Federated credential subject

audiences:
  - "api://AzureADTokenExchange"
issuer: 
subject: |
  system:serviceaccount:
    azure-alb-system:alb-controller
  • AGC controller pod must mutate Azure resources
  • Token exchange happens at runtime, not at boot
  • No SP client secrets stored in any kube Secret
  • RBAC: Network Contributor on the subnet, MI Operator on itself

MS Docs: Workload Identity

The AGC controller creates and updates Azure resources. Instead of storing an SP secret in a kube Secret, use Workload Identity. The AKS cluster has an OIDC issuer. You create a federated credential on a managed identity, bind it to a kube ServiceAccount, and project the token into the controller pod. The pod exchanges that token for an Azure AD token at runtime. No secret sprawl, aligns with zero-trust.

Phase 00, do not start without these.

Blocker

AGC private cluster support reaches GA, or you sign off on the preview risk in writing.

  • AKS cluster on Kubernetes 1.27 or later
  • Gateway API CRDs v1 installed, not v1beta1
  • Hub-spoke VNets peered, NSGs aligned
  • Azure Firewall UDR present on the AKS subnet
Do not proceed until AGC private cluster support is GA, or you have signed off on the preview risk. Verify the AKS cluster is on Kubernetes 1.27+. Install Gateway API CRDs v1 (not v1beta1). Confirm hub-spoke peering and the firewall UDR. If any are missing, pause and fix before Phase 01.

Phase 02 to 03, network and identity.

  1. 01. Create the delegated subnet for AGC in the spoke VNet
  2. 02. Create a managed identity for the AGC controller
  3. 03. Assign Network Contributor on the subnet, MI Operator on itself
  4. 04. Create the federated credential bound to azure-alb-system/alb-controller
  5. 05. Deploy the AGC Helm chart with the MI client ID set in values.yaml
Use the Terraform or Bicep modules in the repo. The subnet needs Microsoft.ServiceNetworking/trafficControllers delegation. The MI needs Network Contributor on the subnet and Managed Identity Operator on itself. Federated credential subject is system:serviceaccount:azure-alb-system:alb-controller. Deploy the Helm chart, watch the controller logs for identity errors.

Phase 04, deploy AGC.

  1. 01. Apply GatewayClass with controllerName azure.com/alb-controller
  2. 02. Apply Gateway with internal frontend annotation
  3. 03. Wait for AGC to provision the AppGw for Containers resource
  4. 04. Curl the assigned private IP from a hub VM

kubectl get gateway -n infra
# wait for ADDRESS column

az vm run-command invoke \
  -g hub-rg -n hub-jumpbox \
  --command-id RunShellScript \
  --scripts "curl -v http://10.x.y.z"
Apply the GatewayClass. The AGC controller will manage gateways of this class. Apply the Gateway with the internal frontend annotation. AGC will provision an AppGw for Containers resource and assign a private IP. From a VM in the hub VNet, curl the IP to confirm reachability. If unreachable, check NSGs, UDRs, subnet delegation.

Phase 05 to 06, translate and coexist.


kubectl get ingress -A -o yaml > inventory/ingress.yaml

ingress2gateway translate \
  --providers ingress-nginx \
  -f inventory/ingress.yaml > generated/httproutes.yaml

# review every HTTPRoute by hand
$EDITOR generated/httproutes.yaml

kubectl apply -f generated/httproutes.yaml -n staging
# both controllers running, route specific test traffic via AGC

Coexist for 2 weeks minimum. Compare error rates, latency, and request volume per controller before any cutover.

Export all Ingress to a file. Run ingress2gateway against it. Review every generated HTTPRoute by hand. Confirm hostnames, path matching, backendRef names. For each annotation that did not translate, decide how to handle. Apply HTTPRoutes to staging. Run smoke tests. Do not move to production until staging is green.

Phase 09, decommission slowly.

Wait 2 to 4 weeks

Coexistence in production. Watch error rates and latency.

Delete Ingress resources

Source-controlled. Recoverable from git.

Uninstall ingress-nginx Helm release

Then delete the LoadBalancer service.

Update DNS to AGC frontend

Watch TTL. Validate from multiple resolvers.

Do not rush. Run dual-stack in production for at least 2 weeks, ideally 4. Monitor error rates, latency, resource use. If AGC is stable and ingress-nginx is no longer receiving traffic, begin decommission. Delete Ingress resources, uninstall the Helm release, delete the LoadBalancer service. Update DNS to the AGC frontend. Keep the ingress-nginx YAML in git for rollback.
